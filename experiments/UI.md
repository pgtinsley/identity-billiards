# Identity Playground

**Sharing with collaborators:** use the [portable source bundle and cluster
quickstart](SHARING.md) for a fresh environment, model-cache reuse and per-user
GPU allocations.

The primary interface is a local browser UI, backed by the GPU in your interactive
allocation. Jupyter is optional; existing notebooks remain research examples.

## Start on the allocated GPU node

From the Identity Billiards repository root (or `stylegan3/` in an extracted
source bundle), after completing setup:

```bash
UV_CACHE_DIR=.uv-cache uv pip install --python .venv/bin/python -r experiments/requirements-ui-lock.txt
.venv/bin/python -m experiments.face_ui --device cuda --host 0.0.0.0 --port 7860
```

The server prints a URL containing a session token. Keep this terminal and the
GPU allocation alive. A new allocation
may have a different compute hostname; use the hostname printed by the server.
Listening on the cluster network automatically enables token authentication;
the browser receives an HttpOnly session cookie after opening the printed URL.

## Connect from your laptop

In a separate **laptop terminal**, forward port 7860 through the front end you
already use. Substitute your current GPU hostname and cluster account:

```bash
ssh -N -o ExitOnForwardFailure=yes \
  -L 7860:GPU_HOST:7860 \
  YOUR_USERNAME@FRONTEND_HOST
```

Replace `FRONTEND_HOST` with your existing externally reachable front-end hostname.
Open the **token-bearing localhost URL printed by the GPU server** in your laptop
browser. The terminal running the tunnel normally stays quiet. Keep it open.
The front end relays traffic; generation, alignment, projection and video encoding
run in the GPU allocation. No X11 forwarding, remote desktop, browser on the GPU,
or public website deployment is needed. This follows CRC's
[documented compute-node tunneling pattern](https://docs.crc.nd.edu/general_pages/j/jupyter.html).
Use your usual campus VPN/bastion connection if your front end requires it.

If local port 7860 is busy, use `-L 7862:GPU_HOST:7860` and change only the browser
URL's port to 7862. Retain its token. If the interactive job ends, acquire another
GPU allocation, restart the server, and update the hostname/token and tunnel.

### Loopback-only alternative

If SSH to the allocated compute node is permitted, keep the service loopback-only:

```bash
# On the allocated GPU node:
.venv/bin/python -m experiments.face_ui --device cuda --port 7860
```

```bash
# On your laptop:
ssh -N -J YOUR_USERNAME@FRONTEND_HOST \
  -L 7860:127.0.0.1:7860 YOUR_USERNAME@GPU_HOST
```

Then open `http://127.0.0.1:7860/`. This mode does not require the generated token
unless `FACE_UI_ACCESS_TOKEN` is explicitly set.

## What to try

1. The UI prepares the learned **W mean** on first load. This remains the default.
   The generated center and fixed reference are displayed side by side.
   Seed-based starts use truncation **ψ = 0.75**:
   `w_center = w_avg + 0.75 * (mapping(z) - w_avg)`.
   Truncation applies once to the starting W vector, not to each trajectory point.
   PCA axes are fitted to untruncated W samples, so step-size units stay unchanged
   across mean, seed and projected centers. Mean and upload starts are unchanged.
   The CLI uses the same seed default; run metadata records both generation and
   PCA-basis truncation separately. In Z-space experiments, mapping truncation
   instead applies whenever a Z coordinate is rendered.
2. Adjust **step size**, **maximum cosine distance**, **reflection policy**, and
   video length, then generate a trajectory. The default distance is 0.55,
   equivalent to similarity 0.45. Smaller distance means a tighter match.
3. Try the same seed/settings with each reflection policy. Motion randomness is
   reproducible with the motion seed. Speed is constant in slice coordinates.
4. Choose **Upload** and select one face. The selected photo appears immediately
   as a local preview; it is not yet aligned or projected. Click **Align & project
   photo** to upload and prepare it. The UI aligns the face,
   projects it into shared W, and shows the aligned reference and reconstruction.
   Inspect their ArcFace match score before generating. Use 250 steps first;
   500–1000 can improve a difficult fit. Use the already-aligned option only for
   square FFHQ-style crops, including images generated by this model.
5. Download the MP4, latent trajectory/embeddings and metadata. This-session
   history lets you view earlier runs. Output files survive server restarts;
   prepared centers and interactive history are in memory, so prepare again after
   restarting. Cancel stops at the next compute checkpoint.

| Policy | Direction at a collision | Useful for |
| --- | --- | --- |
| Mirror | Specular reflection around the estimated inward normal | Smooth billiard paths and a deterministic baseline |
| Random inward | A seeded random unit direction in the inward hemisphere | Broader coverage and avoiding repeated orbits |
| Toward center | Aim at the fixed center; use the inward normal if necessary | Long chords and frequent returns to the starting likeness |
| Glide along boundary | Incoming tangent plus a small inward component | Exploring faces near the match threshold |

Invalid detections or unreliable normals still reverse the direction. Collision
limits, outer-radius hits and fallbacks are recorded and displayed separately.
Collision backoff points are checked too; if a small inset is rejected by the
non-smooth matcher, the last verified contact point is retained and the collision
records `backoff_rejected`. Only evaluated, accepted positions become frames.
These are alternative constant-speed direction rules, not a physical dynamics
engine or uniform statistical samplers. All motion stays in a 2D PCA slice of
shared W. Layer-independent W+, physics dynamics, and source-to-target trajectory
planning are deferred.

## Alignment and projection details

Alignment uses InsightFace's five landmarks and an FFHQ-style oriented eye/mouth
crop with reflected edge padding. It is an approximation to FFHQ's original
68-landmark preprocessing, not the tight 112px ArcFace recognition crop. Uploaded
images receive EXIF orientation correction; no-face and multi-face images are
rejected. Single images are limited to 10 MB and 25 megapixels.

Projection starts from `mapping.w_avg` and optimizes **one shared W vector** with
Adam, VGG16 LPIPS, a coarse pixel loss and weak W regularization. Synthesis noise
and generator weights stay fixed so the resulting center can be reproduced by
the trajectory renderer. The VGG16 model downloads from NVIDIA on first use if
not already present. This differs from NVIDIA's full projector, which also
optimizes synthesis noise. See the
[official projector](https://github.com/NVlabs/stylegan2-ada-pytorch/blob/main/projector.py)
and [FFHQ alignment](https://github.com/NVlabs/ffhq-dataset/blob/master/download_ffhq.py).

For uploads, matching uses the **aligned uploaded face** as the fixed reference,
not the reconstruction. A trajectory is rejected if its reconstructed center
does not meet the selected threshold. A shared-W projection cannot exactly
reconstruct every face, expression or background; visually inspect the fit and
match score. Projection quality and latent-space geometry are separate effects.

### Synthetic inversion controls

Generate known-shared-W targets with the same generator, constant noise and
seed truncation as the UI:

```bash
.venv/bin/python -m experiments.generate_inversion_targets --device cuda
```

The default set contains seeds 0–9, 23 and 42 at psi 0.75, without additional
alignment. `outputs/inversion-targets-psi075/` contains individual PNGs in
`images/`, a labeled contact sheet, exact latents in `latents.npz`, a model/hash
manifest and `synthetic-inversion-targets.zip`. Every saved W is rerendered to
verify pixel-for-pixel agreement with its PNG. Seeds are not filtered by detector
results; detection validity is recorded in the manifest.
Generation enables deterministic CUDA operations and disables TF32; these flags
are recorded in the manifest. Match them for strict pixel comparisons, since
ordinary UI rendering can otherwise differ slightly through floating-point
roundoff even with the same W and constant noise.

Upload an **individual PNG** and check **Photo is already an FFHQ-aligned crop**.
Do not upload the contact sheet or apply alignment again: that changes the
target and no longer tests recovery of the exact original generation. Judge
reconstruction and identity as well as latent error; inversions need not be
unique, and the PNG target is quantized to 8 bits. This generates controls only;
it does not run inversion automatically. Choose a new `--output` to regenerate
without overwriting an existing set; `--seeds` and `--truncation-psi` are optional.

### Alternatives to the current inversion

The current fit has only 512 free values (one shared W), uses no identity loss,
and starts only from the mean. More optimization steps do not remove those
representation and objective limitations. Options worth comparing:

| Option | What changes | Implication for these experiments |
| --- | --- | --- |
| W+ optimization with layer regularization | One W per synthesis layer instead of one shared W; keep generator/noise fixed | Our first proposed comparison on the existing 256px checkpoint. More expressive, but not guaranteed to fit every upload; label W and W+ results separately. |
| [pSp](https://github.com/eladrich/pixel2style2pixel) / [ReStyle-pSp](https://github.com/yuval-alaluf/restyle-encoder) | Learned W+ encoder; ReStyle predicts residual corrections in a few encoder passes | Candidate for faster, reconstruction-oriented starts without hundreds of per-photo gradient updates. |
| [e4e](https://github.com/omertov/encoder4editing) / ReStyle-e4e | Encoder designed around the reconstruction/editability tradeoff | Useful comparison when a faithful reconstruction becomes less natural under motion; not automatically a better pixel fit. |
| [PTI](https://github.com/danielroich/PTI) / [HyperStyle](https://github.com/yuval-alaluf/hyperstyle) | Tune generator weights per image, or predict weight offsets | Candidates for closer reconstructions, but change the generator defining the region. Treat as a separate experiment, not the same latent geometry. |

These alternatives are surveyed, not installed or selectable in the UI yet.
The linked standard FFHQ encoder releases are paired with 1024px generators;
their latent codes are not assumed compatible with our independently trained
256px generator, even if the W dimension matches. Use the encoder's matching
generator (and downsample for display), or train an encoder for our checkpoint.
Architecture support for `output_size=256` alone does not make a pretrained
1024px encoder a compatible inversion of our model.

Suggested first comparison: shared W versus regularized W+ on the same uploads,
same fixed 256px generator, same noise and comparable compute budgets. Compare
visual fit, LPIPS, identity score, runtime, and local motion naturalness. For W+
centers, a controlled first slice can apply the same W-PCA displacement to every
layer; do not claim it samples all of W+. Compare reference versus reconstruction
separately from the subsequent trajectory's minimum similarity. If adding a
differentiable identity loss, also evaluate with a held-out matcher to check
whether improvements generalize beyond the optimized recognizer. Our ONNX
InsightFace evaluation path is not itself an autograd loss.

The service uses one background GPU worker, keeping the browser responsive while
serializing model access. Serving static files and polling jobs do not consume
GPU inference. Files live in `outputs/ui/<job-id>/`. Projection outputs include
`projection.npz`, `projection.json`, `aligned.png`, and `reconstruction.png`.
Run outputs include the existing video, boundary map, trajectory and provenance.
`requirements-ui-lock.txt` pins the browser UI's Linux/Python 3.11 dependencies;
it does not require Jupyter. No frontend build, Node.js, or external fonts/CDNs
are needed.
